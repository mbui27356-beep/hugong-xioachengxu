# 陪护预约小程序与后台管理系统｜开发文档 V1.0

日期：2026-10-26  
用途：产品需求、开发拆分与验收依据，可直接交给开发者或 AI 编程工具。  
技术方向：微信原生小程序 TypeScript；管理后台 Vue 3 + TypeScript；业务后端 TypeScript + Node.js；未来部署微信云开发。  
当前交付为设计文档，不代表系统、支付或云环境已经搭建。

## 1. 项目目标与范围

让患者或家属选择医院、院区、科室和陪护套餐，填写预约与就诊人信息，提交预约，完成微信支付，并查看订单与消息。公司通过网页后台维护服务目录、确认预约、安排护工、处理退款及发送通知。

首期以“宜昌市中心人民医院”为拟配置医院，名称沿用用户与参考图；医院准确名称、院区、科室、地址及可开展服务范围须由运营核实后录入。参考图中的其他公司、电话、150/200/220 元价格均不作为本项目正式数据。不预置任何未经确认的合作关系。

### 1.1 已明确与暂定项

| 项目 | 决定 |
|---|---|
| 城市、医院、等级、院区、科室 | 全部通过后台维护，前端不写死 |
| 患者端 | 微信小程序，预约陪护／订单／消息三个主入口 |
| 管理端 | 独立网页后台，电脑使用为主，兼顾手机查看订单 |
| 云资源 | 现阶段不接真实云函数、云数据库、云存储；开通后接入 |
| 支付 | 正式版接微信小程序支付，当前仅设计接口与模拟状态 |
| 收款主体 | 暂按单一公司自营收款设计，不做多商户平台和自动分账 |
| 首版订单模式 | 建议先确认可安排人员，再开放付款；属于建议默认，正式运营前确认 |
| 护工端 | 首版不单独开发，由调度员在后台维护人员与履约记录 |
| 消息 | 首版站内通知，后接微信订阅消息；不做即时聊天系统 |

### 1.2 首版必须做与后续再做

首版必须做：可配置目录、服务套餐、协议确认、就诊人、报价、预约订单、人工确认与派单、支付和退款闭环、站内消息、角色权限、操作日志、异常提示。

后续再做：护工独立端、自动排班、优惠券、积分、公开评价、多公司入驻、自动工资结算、医院 HIS 对接。首版保留“联系客服／申请售后”；评价可以暂不显示，避免出现无功能的“待评价”。

## 2. 用户流程

1. 打开小程序，在医院选择页按名称搜索，按城市和等级筛选。
2. 进入医院，选择院区、科室；存在病区或护理单元时再选病区。
3. 点击“选择服务”，阅读预约及服务知情说明并主动确认。
4. 选择到岗时间、服务天数或班次，填写照护需求评估，选择套餐。
5. 选择或新增就诊人，补充联系人、病房及床号。
6. 进入最终确认页，检查地点、患者、服务内容、起止时间、费用明细和取消规则。
7. 提交预约，后台确认人员和服务条件，用户收到待付款通知。
8. 用户完成微信支付，后台安排履约，订单进入待服务、服务中、已完成。
9. 用户在订单详情联系公司、申请取消或退款，在消息中心查看进度通知。

“确认订单”应分清两个动作：进入订单核对页不创建正式订单；点击最终“提交预约”才落库。就诊人信息必须在最终提交前收集完成。

如果未来开放立即付款，流程改为提交后进入待支付，但必须先具备可验证的可售时段与服务容量。不能仅因为用户付了钱就承诺有人到岗。

## 3. 小程序页面需求

| 页面 | 展示与操作 | 关键规则 |
|---|---|---|
| 医院选择 | 搜索框、等级筛选、城市筛选、医院卡片 | 支持组合筛选、清空条件、分页、无结果及加载失败重试 |
| 院区／科室 | 医院名、切换医院、院区标签、科室及病区列表 | 必须选到可服务位置才能下一步；上级变化清空不兼容下级选择 |
| 知情说明 | 服务提供方、预约规则、计费规则、取消退款、服务边界 | 不默认勾选；可关闭返回；记录所确认版本；不是自动生成免责结论 |
| 服务选择 | 到岗时间、天数、结束时间、需求评估、套餐卡片 | 时间和人数限制由后端校验；套餐仅展示适用地点及已发布版本 |
| 就诊人管理 | 新增、编辑、选取、设默认、移除常用档案 | 就诊人归属当前账号；不因修改档案而改写历史订单快照 |
| 订单核对 | 医院到床位、就诊人摘要、时间、套餐、逐项费用 | 显示最终金额、退款规则、联系方式，提交前重新报价 |
| 提交结果／支付 | 预约编号、当前状态、付款按钮、联系公司 | 待确认不可付款；支付结果以服务端核实为准 |
| 订单列表 | 全部、待确认、待支付、待服务、服务中、已完成、售后 | 默认展示当前账号全部订单，可按就诊人过滤；空列表有预约入口 |
| 订单详情 | 时间线、费用、联系人、服务安排、支付退款记录 | 依据状态显示取消、支付、申请退款、续费入口，不能任意修改状态 |
| 消息中心／详情 | 标题、摘要、时间、未读角标、关联订单 | 标记已读；无权限或已失效链接需有提示 |
| 协议与帮助 | 隐私说明、服务协议、客服、个人资料管理入口 | 无“我的”标签时放在预约页菜单或订单页工具入口 |

### 3.1 目录层级

城市 → 医院 → 院区 → 科室 → 病区／护理单元（可选）。医院等级为独立字典，关联医院。区县作为城市下一级字段，不把“市辖区”和“宜昌市、武汉市”并列成城市。

医院卡片显示医院名、等级、展示地址；具体到岗地址以选定院区为准。只有一个院区时可以默认选中，但要展示名称。只有科室没有病区时不强迫用户选择虚构病区。医院或院区关闭后不能新下单，历史订单仍显示原信息。

### 3.2 知情说明

参考图体现的是“阅读并确认”，不一定需要用户手写全文。首版采用协议正文加明确勾选与确认按钮。若业务确需签名，再增加签署人、代签关系、签名文件及专门签署方案；不能把点击确认描述成已经完成可靠电子签名。

服务说明、隐私告知、患者信息授权分别说明用途。后台草稿可以修改，发布后形成不可覆盖的新版本；订单保存版本 ID、内容摘要哈希及确认时间。浏览时可先确认，最终提交时由服务端验证已确认版本仍适用；有重大变动则重新确认。

不要照搬参考图“22:00—07:00 禁止下单”。把营业时间、最短预约提前量、临时停单开关做成配置，由公司决定；页面与后端执行同一规则。

### 3.3 需求评估与套餐

评估项可包含：起身行走、翻身换位、表达不适、进食饮水、洗漱如厕；默认均未选择，选项为可以／需要协助／不确定。结果仅用于安排与人工确认，不给出医学诊断，不自动承诺某档护理等级。

套餐字段：名称、服务类型（一对一／一对多）、适用地点、服务内容、明确不包含项目、服务时长、单价、计费单位、预约限制、咨询电话、适用条件、上架状态。不同价格的同名套餐必须用时长或适用条件区分。复杂情况进入人工确认，不在后台悄悄涨价后直接扣款。

### 3.4 就诊人与联系人

建议字段：姓名必填；性别按服务需要填写；年龄或出生日期按需要采集；联系人姓名、联系电话及与就诊人关系必填；病房、床号允许“暂不确定”，但到岗前应补齐。手机号检查格式不等于完成真实号码验证。

首版不默认采集身份证照片、病历图片或完整身份证号。如果确有身份核验要求，再明确用途、访问范围和保存期限。家属代下单与患者本人区分，保存代填关系及授权确认。常用就诊人只对创建账号可见，不能用姓名或手机号匹配后自动共享档案。

## 4. 后台管理系统

后台是给公司人员使用的网站；“后台页面”和“后端服务”是两件事。网页提供按钮、表格与表单，Node.js 后端负责鉴权、查数据、算价格、变更订单。未来两端共用云端业务和数据库。

| 菜单 | 功能 |
|---|---|
| 工作台 | 待确认、待派单、今日到岗、退款待处理；区分预约金额、实收金额与已退金额 |
| 服务地区 | 城市及区县新增、编辑、排序、启停；有下级引用时禁止直接硬删除 |
| 医院管理 | 医院等级字典、医院、院区、地址、联系方式、营业状态 |
| 科室管理 | 院区内科室与病区维护；批量排序；防止跨院区错误关联 |
| 服务套餐 | 内容、价格版本、计费单位、有效期、适用地点、上下架 |
| 预约订单 | 筛选搜索、查看详情、确认／拒绝、取消、备注、到岗与完成操作 |
| 护工与调度 | 人员、服务地点、可用班次、派单、改派、冲突提示、到岗记录 |
| 支付退款 | 支付流水、退款审核及执行、失败重试、账单核对、异常处理 |
| 就诊人资料 | 仅为处理相关订单查看所需资料，默认脱敏，限制导出 |
| 消息管理 | 选定用户或订单发送站内通知、查看发送记录；订阅消息另设渠道状态 |
| 协议配置 | 服务说明、隐私告知、取消退款规则的草稿、预览、发布与版本历史 |
| 系统设置 | 服务提供方、客服、营业时间、预约提前量、付款期限、角色与日志 |

### 4.1 角色及数据范围

超级管理员管理账号与全局配置；运营维护目录和套餐；调度处理其负责医院的订单与派单；财务查看支付和执行获授权的退款；客服查看授权订单并发送通知。首期同一员工可拥有多个角色，但权限模型必须保留。

登录后由服务端检查角色和医院范围，不能仅隐藏前端按钮。敏感资料查看、订单改价、退款、导出及权限变更记录操作者、时间、对象和原因。退款操作至少有明确权限和确认步骤，大额双人审核作为可配置扩展。

### 4.2 最小履约闭环

订单进入待确认 → 调度联系家属并核实需求 → 预留人员或班组容量 → 开放付款 → 支付成功转正式占用 → 记录具体安排 → 到岗开始 → 服务结束。

一对一不允许同一护工在重叠时段重复指派。一对多以班组、班次和最大服务人数管理容量，不用“一人只能有一单”的规则误拦。首期人工调度，系统仍需冲突提示。取消、拒绝或付款超时应释放预留容量。改派保留历史，不覆盖原派单记录。

## 5. 计费、订单与退款规则

### 5.1 计费必须先定义

“一天”是连续 24 小时、自然日还是一个班次，需要在真实收款前确认。开发演示默认每单位 24 小时，不将其视为已确认营业规则。例如 10 月 26 日 15:00 起 1 天，演示结束时间为 10 月 27 日 15:00；不能直接设为当天 23:59:59。

金额使用整数分，不能用浮点元参与结算。业务时区为 Asia/Shanghai，数据库时间使用统一 UTC 时间戳，展示转换为北京时间。服务区间用开始包含、结束不包含，避免相邻班次重叠。

服务端根据地点、套餐价格版本、开始时间、数量和附加费计算报价。客户端只能提交套餐 ID 和数量，不能决定单价或实付金额。报价设置有效期；价格变化时显示差异并让用户确认。旧订单保留价格与服务内容快照，不随后台改价变化。

节假日加价、夜间费用、首尾不足一天、提前结束、续费必须有明细规则；规则未确认时不启用自动加价或自动扣款。续费首版创建关联新订单，重新确认容量与价格。

### 5.2 状态拆分

| 维度 | 状态 |
|---|---|
| 业务状态 | PENDING_CONFIRM 待确认、PENDING_PAYMENT 待支付、PENDING_SERVICE 待服务、IN_SERVICE 服务中、COMPLETED 已完成、REJECTED 已拒绝、CANCELLED 已取消 |
| 支付状态 | UNPAID 未支付、PAID 已支付、PARTIALLY_REFUNDED 部分退款、REFUNDED 全额退款 |
| 单笔退款状态 | REQUESTED 已申请、APPROVED 已批准、PROCESSING 处理中、SUCCEEDED 成功、REJECTED 驳回、FAILED 失败 |

业务和资金状态独立。例如取消但退款处理中，不能显示“退款已完成”；服务完成后部分退款，也不能将服务状态错误倒退为待服务。

| 动作 | 前置条件 | 结果 |
|---|---|---|
| 提交预约 | 身份、资料、有效报价、协议及可服务地点通过检查 | 待确认 |
| 调度确认 | 需求确认、容量预留成功，记录付款截止时间 | 待支付 |
| 调度拒绝 | 尚未付款，填写理由 | 已拒绝，通知用户 |
| 支付成功 | 服务端验证交易与金额，状态原子更新 | 已支付、待服务 |
| 开始服务 | 已支付且有效安排存在 | 服务中，记录实际开始时间 |
| 结束服务 | 服务中，记录实际结束与完成凭据 | 已完成，发送通知 |
| 取消未付款订单 | 尚未成功付款，处理支付中竞态 | 已取消，关闭支付单，释放容量 |
| 已付款取消／提前结束 | 根据规则核算未服务部分，财务审核 | 取消或结束业务，同时创建独立退款记录 |

重复点击用请求幂等键防重复下单；状态改变带版本号或条件更新，防止两个管理员同时处理。付款截止前后必须先与支付渠道核对，不能本地倒计时结束就认定没有付款。迟到的成功支付通知进入补偿处理：核实交易，若已不能履约则安排退款并通知。

### 5.3 退款

首版支持未服务全额退款与按核准规则部分退款。用户提交原因，后台审核，服务端发起原路退款，收到可信结果后更新状态。退款单号唯一、重试复用；退款成功金额和进行中预留金额之和不能超过实收金额。失败进入待人工处理，不能再次生成相同金额的新退款造成重复退。

取消时限、扣费方式、已服务时长的折算是业务待定项；上线前写入规则并让用户看到，不由开发者自行编造收费比例。

## 6. 技术架构与分阶段接入

### 6.1 推荐技术

| 部分 | 选择及理由 |
|---|---|
| 小程序 | 微信原生 + TS + WXML + WXSS，贴近参考页面及微信能力 |
| 网页管理端 | Vue 3 + TS + Vite，表单与表格组件库按开发时维护情况选择 |
| 后端业务 | TS 编译为 JS，在 Node.js 环境运行；按业务模块组织 |
| 最终数据 | 云开发数据库，保存结构化记录 |
| 最终文件 | 云存储，保存医院图标及必要文件，数据库保存文件标识 |
| 本地验证 | Mock 数据与服务适配层；需要两端联动时增加本地 Node.js 演示 API |
| 部署 | 小程序提交微信；后台静态资源托管；业务接云函数，必要时使用 HTTP 云函数入口 |

云函数本身就能运行 Node.js 业务，不必为了使用 TS + Node.js 再租一台服务器。具体运行时、SDK、数据库事务及 HTTP 能力在云环境可用后核实并锁版本。[S1][S2]

### 6.2 当前阶段：云能力不接入

先实现页面、导航、表单校验、后台增删改查界面、订单状态演示、模拟消息及错误状态。开发数据明确标注“演示”，只用虚构患者与电话。图片使用本地占位资源。

分别使用各自本地 Mock 时，小程序和网页的数据不会自动同步。如果要演示“后台新增医院，小程序立刻能看到”，启动同一个本地 Node.js API，两端都访问它。该 API 只用于开发；开发工具的本地网络配置不等于正式发布条件。演示数据可用本地文件持久化，真实业务数据库接通后替换仓储实现。

不在这个阶段调用真实支付、保存真实患者资料或向真实用户发消息。生产构建禁止导入 mock 支付与 mock 管理员身份。

### 6.3 云开通后

1. 创建隔离的测试和生产环境，配置资源预算与告警。
2. 建立集合、索引、权限及初始管理员。
3. 将仓储实现替换为 CloudBase；部署 TS 编译后的 Node.js 函数。
4. 小程序通过受信的云调用上下文获取身份；后台通过独立管理员认证调用受保护接口。
5. 接入云存储，限制上传文件类型和大小；敏感文件不使用永久公开链接。
6. 接微信支付、退款、查询与回调；接站内消息和订阅消息任务。
7. 真机联调与受控小额支付退款验收后，准备正式审核。

两端共用业务模块，传输入口可不同：小程序使用云调用适配器；网页使用已验证登录态的 HTTPS/CloudBase 接口。浏览器不能放服务器密钥，也不能自行传一个 openid 就被视为该用户。

## 8. 接口约定

下列是逻辑接口名称，可映射为 HTTP 路由或云函数 action，避免页面绑定具体部署方式。

| 接口 | 输入／结果 | 权限或规则 |
|---|---|---|
| catalog.listHospitals | keyword、cityId、gradeId、cursor → items、nextCursor | 仅返回启用目录 |
| catalog.getHospitalTree | hospitalId → 院区／科室／病区 | 可按院区懒加载 |
| catalog.listOfferings | locationIds → 套餐与价格摘要 | 校验地点父子关系 |
| agreements.getPublished | type、scope → 有效正文与版本 | 不返回未发布版本 |
| patients.create/update/list | 必要患者资料 → 档案 | 身份与归属校验 |
| orders.quote | offeringId、location、startAt、units、assessment → quoteId、明细、expiresAt | 服务端算价 |
| orders.create | quoteId、patientId、contact、bed、consents、requestId → orderId、status | 重新校验报价、协议及营业规则 |
| orders.list/detail | cursor、筛选／orderId → 脱敏订单 | 只能查当前用户订单 |
| orders.cancel | orderId、reason、version → 最新状态 | 付款竞态核对 |
| payments.prepare | orderId → 微信支付所需参数 | 仅本人且待支付，金额取订单 |
| payments.query | orderId → 服务端核实的支付状态 | 不采信客户端支付成功标志 |
| refunds.request | orderId、reason → 售后申请 | 不允许用户决定退款执行金额 |
| messages.list/read | cursor／messageId → 消息 | 只能读本人消息 |
| admin.catalog.* | 目录增改、启停、发布 | 运营权限与范围 |
| admin.orders.confirm/assign/start/complete | orderId、version、操作数据 | 对应角色、条件更新、审计 |
| admin.refunds.approve/execute | refundId、核定金额、reason | 财务权限、退款额度检查 |
| admin.messages.send | 指定对象、内容 → 发送记录 | 校验目标范围并审计 |
| payment/refund notify | 渠道签名消息 → 确认响应 | 验证渠道来源，幂等处理 |

统一响应：成功为 `{ ok: true, data, requestId }`，失败为 `{ ok: false, error: { code, message }, requestId }`。常用错误码：AUTH_REQUIRED、FORBIDDEN、VALIDATION_FAILED、NOT_AVAILABLE、PRICE_CHANGED、AGREEMENT_CHANGED、STATE_CONFLICT、PAYMENT_PENDING。生产响应不包含堆栈、密钥或完整患者资料。

示例类型（接口草案，非完整可运行代码）：

```ts
interface CreateOrderInput {
  quoteId: string;
  patientId: string;
  contact: { name: string; phone: string; relationship: string };
  bed?: { room?: string; bedNo?: string };
  consents: Array<{ agreementId: string; version: number }>;
  requestId: string;
}
// userId/openid 从认证上下文取得，不接受页面自报作为授权依据。
// totalFen 从有效报价和服务端业务规则取得，不由客户端传入决定。
```

## 9. 微信支付与消息

### 9.1 支付接入

云开发开通和微信支付开通是不同事项。需要核实企业小程序认证、可用商户号、小程序绑定、所选支付方案的凭证与回调配置。普通公司自营业务优先采用适用的直连商户方案，最终以商户平台实际获批能力为准。[S3]

支付链路：服务端创建支付单 → 小程序调起微信支付 → 微信通知受保护的服务端入口 → 验签和解密、核对商户/AppID/订单/金额/币种 → 幂等更新支付和订单 → 写入通知任务。若采用平台托管支付集成，确认其承担的验签边界，禁止公网绕过后直接调用内部通知处理器。

前端支付返回成功仅用于显示“正在确认”，随后查询后端。回调可能重复或延迟；交易查询与定时对账用于补偿。密钥仅存服务端密钥配置，不提交 Git，不放网页或小程序代码。[S4]

公司收款和护工收入结算分开记录；工资、佣金或劳务结算不属于本次微信收款接口功能。首版可导出经过授权的结算汇总，具体分配比例不在代码中写死。

### 9.2 消息接入

站内消息是数据库记录，后台可向指定客户或订单发送业务通知，用户进入小程序查看。微信订阅消息是另一渠道，需要适用模板及用户授权，不能承诺管理员输入任意文本就能无限推送到用户微信。[S5]

首版事件：预约提交、预约确认待付款、预约拒绝、支付确认、人员安排、改派、服务开始／完成、退款进度。消息内容尽量不含健康详情和完整身份信息。

订单事务内写入待发送任务，再由任务处理器投递；通知失败不能回滚已完成付款。对 eventKey 去重、记录重试与最终失败；用户拒绝订阅不影响站内消息和预约。紧急事项保留电话联系，不依赖订阅消息送达。

## 10. 数据保护与运行准备

以下为产品与工程要求，不替代最终协议及经营审核：按服务需要最少采集患者资料；清楚告知用途和访问范围；资料展示脱敏；后台按角色和医院隔离；敏感字段与文件采用适当加密和访问控制；日志不记录完整身份证、电话和健康评估内容。

制定资料保留、删除申请、备份与恢复规则；删除常用就诊人不应误删必要交易记录，历史记录保留范围需另行确认。测试与生产隔离，不复制真实患者资料到演示环境。上线前落实小程序实际服务类目、所需资质、备案及隐私设置，以平台当前审核要求为准。

错误监控至少覆盖：下单失败、回调失败、已支付未入账、退款长期处理中、无人派单、通知积压。每日检查收款与退款差异。定期验证备份能够恢复，管理员离职及时停用账号。

## 11. 开发任务与验收

| 阶段 | 任务 | 完成标准 |
|---|---|---|
| A 规则定稿 | 明确计费单位、付款时机、取消规则、初始目录 | 有可执行示例，不含冲突规则 |
| B 无云原型 | 小程序流程与后台页面，模拟身份、订单、消息 | 虚构用户完整走完预约；后台可维护目录并演示处理 |
| C 本地联动（可选） | Node.js 本地 API 统一模拟仓储 | 后台新增医院后小程序重新加载可见；重启行为有说明 |
| D 云端接入 | 真实认证、数据库、存储、权限与审计 | 两个账号数据隔离；客户端不能改价格或越权查询 |
| E 支付通知 | 真实支付、查单、退款、对账、订阅消息 | 受控真机支付和退款成功，重复回调不重复处理 |
| F 试运营 | 实际运营资料、调度培训、告警与备份 | 少量订单完成预约、派单、服务及售后闭环 |

### 核心验收用例

1. 后台新增城市、医院、院区、科室和套餐，小程序无需改代码即可显示；关闭上级后下级不可新预约。
2. 切换院区后旧科室和套餐被清除；伪造跨医院组合被后端拒绝。
3. 未确认协议不能提交；协议更新后旧确认按规则重新提示。
4. 未选评估项、不合法时间、负数天数、错误电话均有清晰提示。
5. 修改客户端价格无效；后台改价不改变历史已创建订单；过期报价重新确认。
6. 双击提交与网络重试只创建一个订单；断网后恢复可查询原订单。
7. 用户 A 无法查询或修改用户 B 的患者、订单、支付和消息；调度员无法绕过医院范围。
8. 待确认不能支付；付款成功但前端断网，再进入能恢复正确状态。
9. 重复支付通知只记一次；假签名、错金额或错商户不进入已支付；迟到回调进入补偿。
10. 付款超时与付款成功并发时最终资金和业务状态一致，人员预留不永久占用。
11. 一对一重叠派单被阻止，一对多容量满后不能超额安排；取消释放容量。
12. 部分退款、退款失败重试和重复通知不造成超退；退款未完成不显示成功。
13. 拒绝订阅仍可下单且站内消息正常；发送失败可以重试而不重复产生业务订单。
14. 真机测试长科室名、大字体、底部安全区、键盘遮挡、弱网、空列表及返回上一步保留表单。
15. 生产构建不能启用模拟支付、模拟管理员或本地假身份；备份恢复演练通过。
